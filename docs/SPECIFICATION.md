# Random Picker 正式仕様書

- 対象: `sakai-kon/Random-Picker`
- 基準実装: 2026-09-09 時点の `index.html`（単一HTML構成）
- 目的: 既存の仕組みを維持しながら、じゃんけん大会を参加者登録から優勝決定・結果出力まで安全に進行できるようにする。

## 1. プロジェクトの目的

Random Picker は、登録した参加者を使ってじゃんけん大会をブラウザだけで進行・記録する Web アプリケーションである。外部サーバーや有料APIを必要とせず、ブラウザの `localStorage` を大会状態の保存に利用する。

最重要要件は、現在の試合が終了したことと大会全体が終了したことを混同せず、最後の決勝で優勝者が1人に確定するまで大会状態を維持することである。

## 2. 現状調査

### 2.1 ファイル構成

現行の公開実装は単一の `index.html` で構成される。HTML、CSS、JavaScriptを同一ファイルに置く構成であり、フレームワークや外部ライブラリへの依存はない。

今回、仕様書のみを `docs/SPECIFICATION.md` として追加する。アプリ本体は既存の `index.html` を維持する。

### 2.2 エントリーポイント

`index.html` が GitHub Pages 等で直接配信されるエントリーポイントである。

### 2.3 画面構成

アプリは複数HTMLページではなく、1ページ内のセクションを状態に応じて表示する構成である。

1. 参加者登録・大会設定
2. 大会進行
3. 対戦結果・大会結果

独立した「プレイ」ページは存在しない。大会進行セクションを大会開始後に表示するため、データのない進行ページを単独ナビゲーションにする必要はない。

### 2.4 使用技術

- HTML5

- `localStorage`
- Clipboard API（利用できない場合は旧式コピー処理へフォールバック）

外部API、外部DB、フレームワーク、新規ライブラリは導入しない。

## 4. 大会データ構造

既存のデータ構造を優先し、不要な再設計は行わない。

概念として以下を使用する。

```text
Tournament
├─ version
├─ players[]
├─ rounds[]
│  ├─ name
│  └─ matches[]
│     ├─ a
│     ├─ b
│     └─ winner
├─ currentRound
├─ champion
├─ status
├─ groupMode
├─ createdAt
└─ updatedAt
```

`players` は `{ id, name, gender }`、試合は参加者IDを参照する。

ラウンド数は参加者数以上の最小の2のべき乗を基準に決定する。空き枠は不戦勝として扱う。

## 5. 参加者登録

### 入力形式

1行につき `苗字 名前,性別` とする。

区切り文字は `,`、`，`、`、` に対応する。名前中の空白は正規化し、半角・全角・Unicode空白を許容する。

### エラー

- 0人または1人 → 大会開始不可
- 256人超 → 大会開始不可
- 区切り文字なし → エラー表示
- 名前なし → エラー表示
- 性別なし/未対応値 → エラー表示
- 同一名 → エラー表示

## 6. 大会開始

大会開始時に参加者を解析し、選択された組み方で並べ替えてトーナメントを生成する。

参加者数が2のべき乗でない場合は、次の2のべき乗まで空き枠を作る。空き枠との試合は不戦勝として自動確定する。

## 7. 大会進行

大会状態は必ず次の順序で遷移する。

```text
参加者
  ↓
第1回戦
  ↓
勝者一覧
  ↓
次ラウンド生成
  ↓
準々決勝 / 準決勝等
  ↓
決勝
  ↓
優勝者確定
  ↓
大会終了
```

### ラウンド確定処理

現在ラウンドを確定するときは、次の順で処理する。

1. 現在ラウンドの有効な試合を取得
2. 全試合に有効な勝者が設定されているか確認
3. 勝者一覧を作成
4. 現在ラウンドが最後のラウンドか確認
5. 最終ラウンドなら勝者1人だけを `champion` に設定して終了
6. 最終ラウンドでなければ次ラウンドの試合を勝者から生成
7. `currentRound` を次ラウンドへ進める
8. `localStorage` に保存
9. 画面を再描画

重要: 「現在の試合が終わった」だけでは大会終了にしない。大会終了判定は最終ラウンドに限定する。

## 8. じゃんけん勝敗

既存UIの勝者選択方式を維持する。

- 両者が存在する試合のみ勝者を選択可能
- 選択中の勝者を再選択すると未選択に戻せる
- 不戦勝は自動確定
- 未確定試合が残っている場合はラウンド確定不可
- あいこを含む勝者未確定状態では大会状態を次へ進めない

## 9. トーナメント表

大会進行中は現在までに生成されたラウンドを確認できる。大会終了後は全ラウンドを表示する。

各試合について可能な範囲で以下を表示する。

- ラウンド名
- 試合番号
- 対戦者
- 勝者
- 不戦勝

横幅の大きいトーナメントはコンテナ内スクロールで表示し、iPadでもページ全体を崩さない。

## 10. 大会結果

大会終了後に以下を確認できる。

- 優勝者
- 準優勝者（決勝敗者）
- 全ラウンドの対戦履歴
- トーナメント表

## 11. 結果書き出し

外部サービスを使わず、ブラウザ内だけで結果を出力する。

### TXT

人が読みやすい大会結果を `.txt` で保存する。

### JSON

大会の主要結果を構造化データとして `.json` で保存する。参加者、各ラウンドの試合、勝者、優勝者、準優勝者を含む。

既存の「結果をコピー」「印刷」も維持する。

## 12. 状態保存

大会状態は既存の `localStorage` キー `randomPickerTournamentV9` に保存する。参加者入力は `randomPickerParticipantsV8` に保存する。

大会状態を読み込む際は最低限の構造検証を行い、破損・不正データは大会として復元しない。破損状態を無理に利用して別のデータ破壊を起こさないことを優先する。

サーバーや外部DBは導入しない。

## 13. ページ/ヘッダー方針

現在は単一ページ構成のため、ページを無意味に分割しない。

上部のブランド表示は共通ヘッダーとして扱う。大会進行は大会開始後のセクションとして表示する。

独立した「プレイ」ナビゲーションは作らない。大会データが存在しない状態で進行画面だけを開く設計にしない。

## 14. iPad対応

以下を維持・確認する。

- タップ可能なボタンは44px以上を基本とする
- 大会進行ではボタンを押しやすくする
- 横幅に応じて試合カードを1列化する
- トーナメントは横スクロール可能にする
- 長い名前がレイアウトを壊さないよう折り返す
- 不要な巨大カードや過剰な余白を避ける
- 印刷時には操作UIを非表示にする

## 15. エラー処理

最低限以下を安全に処理する。

- 参加者0人
- 参加者1人
- 参加者数過多
- 入力形式不正
- 大会データなし
- 破損した大会データ
- 試合データなし
- ラウンドデータなし
- 勝者未選択
- 不戦勝
- あいこ等で勝者未確定
- 大会終了後の進行操作
- リロード
- `localStorage` 保存失敗

アプリをクラッシュさせず、可能な場合は画面上のメッセージで知らせる。

## 16. 最重要バグ防止方針

大会終了条件は以下だけとする。

```text
currentRound === 最終ラウンド
        AND
そのラウンドの試合がすべて確定
        AND
勝者が1人
        ↓
大会終了
```

これにより、途中ラウンドの勝者確定を大会終了と誤認しない。

また、次ラウンド生成先が存在しない・必要試合数が不足しているなどの不正状態では、大会を勝手に終了せずエラーとして停止する。

## 18. テスト計画

### ケース1: 少人数

2～4人で開始し、最終的に優勝者が1人決定すること。

### ケース2: 複数ラウンド

5人以上など、複数ラウンドが必要な人数で、途中で大会が終了せず決勝まで到達すること。

### ケース3: 不戦勝

2のべき乗でない人数を使い、空き枠が不戦勝として処理されること。

### ケース4: 決勝

決勝の勝者を確定した時点だけ `status=finished` となり、`champion` が設定されること。

### ケース5: トーナメント

大会終了後、全ラウンドと勝者がトーナメント表に残ること。

### ケース6: 結果出力

TXT / JSON / コピー / 印刷が利用できること。

### ケース7: iPad表示

狭い幅ではカードが1列になり、トーナメントは横スクロールできること。

### ケース8: 不正状態

大会データがない、または破損している状態で進行処理を行ってもクラッシュせず、安全な初期状態に戻ること。
